# F.16.5.4c — Subscription hold access (implementation contract)

Status: **Policy and authorization scaffolding only.** Not production-enabled or attached to live customer finance endpoints. CI validation still required.

## Business behavior

A subscription can be marked `PAST_DUE` **only by a separately reviewed billing workflow** after the agreed due date, grace period (if any), verified payment reconciliation and contractual entitlement checks. An unpaid due record alone is **not** sufficient to hold the account.

During a reviewed hold, customers can:
- sign in, view a historical dashboard and billing balance;
- view and edit their personal and business profile, subject to role permissions;
- view previous income/expense entries;
- edit only entries that already existed **before the hold began**, with tenant ownership verification and immutable edit audit trail;
- view and download **previously generated, immutable report snapshots** (not live recalculations);
- request payment reconciliation and see restoration instructions.

During a hold, customers cannot:
- create new income or expense entries, invoices, customers' billable transactions or inventory movements;
- generate or recalculate financial reports, or overwrite saved historical report snapshots;
- delete historical accounting entries, manage users, or bypass access controls.

A failed/uncertain payment must be reconciled; never charge twice. Access returns to full functionality only when the trusted subscription settlement or promotion entitlement workflow clears `PAST_DUE`. Do not let the browser or checkout result alone change the status.

## Enforcement

1. API endpoints must authenticate the session, verify the active business membership, permission, business status, and CURRENT subscription status within the relevant transaction.
2. `server/src/modules/subscriptions/subscription-hold-access.policy.ts` provides the capability matrix. No route accepts a customer-supplied capability or resource proof.
3. `server/src/modules/subscriptions/subscription-hold-access.service.ts` reads membership and role permission, then fails closed on missing or unauthorized data. It does not produce proof for editing entries or saved reports.
4. Future transaction-edit services must load an existing row by UUID + business_id, prove it predates an auditable `held_at` timestamp and record before/after changes. **Never use an upsert** for a historical edit.
5. Future report download services must load immutable archived report IDs by business_id with generation timestamp and object integrity, not generate fresh reports on a GET/download request.
6. Reports generated before an accounting edit must remain unchanged and labeled as historical snapshots; the edit audit should identify affected periods without silently modifying downloaded archives.
7. Future UI should display a clear `Account on Hold` banner, overdue months, verified balance, payment review option and the limited-action menu. Buttons are not a security boundary.

## Known repository limitations

- `server/src/routes/transaction.routes.ts` currently responds `503 FEATURE_NOT_READY`; the UUID-based transaction module, historical edit API and audit trail are not implemented yet.
- Report controller/routes and archived report storage are not functional. Previous report view/download cannot be enabled without stored immutable snapshots.
- Subscription status transition to `PAST_DUE`, hold timestamp, grace-period decision, alerts and reactivation are not implemented by this branch.
- Production registration, real gateway payments and live financial posting remain disabled.

Never deploy or enable hold access simply because unit and CI MySQL checks pass. The remaining application endpoints and production billing gates need separate reviews.
