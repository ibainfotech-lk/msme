# Noteto F.17.4c — Unverified taxpayer intake drafts (private development)

**Branch:** `feature/f17-4c-taxpayer-intake-drafts`.
**Base:** F.17.4b source review / MySQL migration fix, workflow #43 green, commit `8f521749e67a9fcd5656d70c5fbaf78d3cf70423`.
**Status:** Private development only; production access disabled. No live tax estimate, payment, filing, legal decision or approved taxpayer verification.

## Goal and strict limits

Allow an authorized business member to record **self-declared, non-identifying** tax preparation answers for the April–March year of assessment, so a tax professional knows what to review next.

- Questionnaire: possible taxpayer type (individual/company/other/unknown), claimed residency, other income outside Noteto cashbook, capital asset purchases (e.g. equipment and furniture), potentially non-deductible costs, withholding credits and whether the owner is personally the taxpayer.
- All fields can be UNKNOWN or NOT_SURE. Any YES, NO or category remains **UNVERIFIED**. An owner's declared residence is not legally verified residence, and declaring a company does not verify the taxpayer's identity.
- Does **not** collect TIN, NIC, passport, national identity data, addresses, personal income amounts, tax rates, tax reliefs, bank accounts, government credentials, tax filing documents or tax due.
- Does not treat capital purchases as deductible cash expenses. Reconciliation of asset capitalization, depreciation and Sri Lankan capital allowances requires expert review.
- Existing F17.4 readiness fields `taxableIncomeLkr`, `taxPayableLkr` and `paymentDueLkr` remain **null**, not 0. No estimate or credit is automatically applied.
- No declaration can be certified or marked reviewed through this feature. A separate documented reviewer workflow, explicit customer consent/privacy terms and proper source evidence are needed.

## Database

New additive migration `20261124_033_taxpayer_intake_drafts` (total **23**).

- `taxpayer_intake_drafts`: unique `(business_id, assessment_year_start)`, revision integer, one enum for each answer, last editor and timestamps; no personal identifiers.
- `taxpayer_intake_draft_audits`: append-only before/after claim snapshots per revision; audited by user and tenant-specific composite FK. Each create/update inserts its audit record in the **same database transaction**.
- `taxes.manage` permission is created if absent but is **not granted** to any existing role. An organization administrator must have a separate security-reviewed role assignment process to enable editing. `taxes.read` alone never grants writes.
- No new changes to cash transactions, invoices, tax rules, subscription payments or immutable report PDFs.

## API, authorization and concurrency

- `GET /api/taxes/businesses/:businessId/intake?assessmentYearStart=2026`
  *Requires authenticated session, `taxes.read`, active business, active membership, active/trial subscription, valid effective dates and the existing report/hold capability. Returns `NOT_STARTED` or `UNVERIFIED_DRAFT`, revision, enumerated claims and explicit false/null verification/payable flags.*

- `PUT /api/taxes/businesses/:businessId/intake` with a strict JSON body:
```json
{
  "assessmentYearStart": 2026,
  "expectedRevision": null,
  "claims": {
    "taxpayerCategoryClaim": "NOT_SURE",
    "residencyClaim": "UNKNOWN",
    "otherIncomeClaim": "YES",
    "capitalAssetsClaim": "YES",
    "nonDeductibleCostsClaim": "NOT_SURE",
    "withholdingCreditsClaim": "UNKNOWN",
    "ownerIsTaxpayerClaim": "NOT_SURE"
  }
}
```
  *Creation requires `expectedRevision:null`. Editing requires the exact previously returned positive revision. Stale writes return HTTP 409 without mutating a stored draft. The endpoint enforces same-origin requests, `taxes.manage` **in addition to** `taxes.read`, and all read-side subscription/hold checks. Extra fields (especially unexpected personal identifiers or amounts) are rejected.*

No DELETE, approval, verification, special tax bracket or arbitrary free-text evidence upload route is added. All operations are tenant-scoped and transactional. A business lock serializes simultaneous first-draft writes; a revision check protects subsequent edits.

## Feature flags

- Server read: `NODE_ENV=development` + `NOTETO_F17_TAX_READINESS_ENABLED=true` (existing F.17.4 tax readiness).
- Server write: **also** `NOTETO_F17_TAX_INTAKE_WRITE_ENABLED=true`.
- React: Vite development + `VITE_NOTETO_F17_BOOKKEEPING_UI_ENABLED=true` + `VITE_NOTETO_F17_TAX_READINESS_UI_ENABLED=true` + `VITE_NOTETO_F17_TAX_INTAKE_UI_ENABLED=true`.
- All other environments fail closed, including production regardless of flags. Do not enable production or bypass a subscription hold.

The React form includes English, Tamil and Sinhala labels. The interface explicitly says responses are unverified and that no IDs or financial amounts are collected. Saving is restricted to authorized roles.

## CI and release limitations

Existing `test:mysql-tax-readiness` is extended from 18 to **26** tests covering:
- Draft absent, self-declared create/read, no payable income.
- Optimistic version update and audit before/after records.
- Concurrent initial saves, one successful draft and audit.
- Denial for another tenant or missing `taxes.manage`, held accounts.
- Rejection of extra PII fields, invalid categories, revisions and production/feature-disabled writes.
- HTTP session, same-origin write, strict payload, CAS replay denial, tenant isolation.

All existing MySQL suites now expect **23** migrations. Run on a disposable MySQL 8.4 CI instance; no local or production migrations should be performed as part of this checkpoint.

**Further work before tax estimation**: formally verify taxpayer identity/classification, independently review all relevant statutory source versions and effective dates, confirm other income and capital adjustments, implement secure evidence collection/consent/retention, approve tax-rate rules with independent tax professional, and test any deterministic estimate against official examples. No user should be given an assumed payable-tax figure based merely on a cash surplus.
