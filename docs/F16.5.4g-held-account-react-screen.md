# F.16.5.4g — Customer-facing Account Hold Mode (private development UI)

Status: **development-only and not yet CI validated**. This change builds from the F.16.5.4f CI-validated backend commit `d553f62`.

## What this branch adds

- A responsive, accessible hold screen in React with English/Tamil/Sinhala labels.
- Server-authenticated access mode at `GET /api/hold-history/businesses/:businessId/access`.
- A hold banner and separate explanations of disabled new income, expenses, invoices and reports.
- Historical income/expense list loaded from business-scoped, pre-hold SQL data.
- Historical entry correction form requiring a reason and optimistic version check; the backend writes its audit.
- Previous report list and download of existing, checksum-verified archived PDFs, not fresh report generation.
- Safely disables this UI until the server returns `HOLD`; uncertain modes/errors never fall back to the normal transaction screen.

The `/api/transactions` routes continue to return 503 and are NOT re-enabled.
No automatic monthly due creation, payment initiation, customer subscription transition or report generation is added.

## Private development switches

The client UI is only compiled into the active route when both `import.meta.env.DEV` is true and `VITE_NOTETO_HOLD_MODE_UI_ENABLED=true`. The flag must be set for the Vite development server, not production.

The backend route mount remains restricted to:
```text
NODE_ENV=development
NOTETO_HOLD_HISTORY_API_ENABLED=true
```
Additional backend checks:
```text
NOTETO_SUBSCRIPTION_HOLD_POLICY_ENABLED=true
NOTETO_HISTORICAL_EDIT_ENABLED=true
NOTETO_ARCHIVED_REPORT_DOWNLOAD_ENABLED=true
```
This is **not** a recommended production configuration. Existing database restrictions still mandate the isolated development database; do not run MySQL integration fixtures locally.

## Security model

The frontend never decides HOLD status from local data. After an authenticated OTP login, it requests the access state from the backend, which verifies current business, subscription, membership and role. A user with a held subscription receives a separate screen with no new-transaction or report-generation controls.

The previous-entry list and archived-report list query only existing same-business records predating `held_at`. The correction endpoint requires the current row version, `transactions.update` authorization and an audit record in one transaction. The PDF endpoint verifies the file's checksum and content type.

The new server-level HTTP integration test covers unauthenticated access, hold-state lookup, past entries, forged and missing Origin headers, a valid audited correction, and rejects POST attempts to create new records or reports.

## Remaining work before production

- The React screen is a private development integration, not a live customer feature. The hold transition and restoration workflow are not implemented.
- An accurate subscription arrears statement must be fetched from verified monthly dues before showing LKR amounts. This UI deliberately does not display guessed balances, penalties or payment buttons.
- Profile editing is not wired yet; the screen shows the current business name and explicitly explains that profile editing requires an authorized backend endpoint.
- Error handling/localized translations, all real HTTP/session/security regression tests, pagination, PDF retention/integrity guarantees, and accessibility audits require additional review.
- Do not enable automatic subscription holds without the reviewed due date, grace period, trial/promotion protection, settlement reconciliation and notices.
- Archived reports must already exist: report generation/storage pipeline is still absent. Prior reports cannot be reconstructed by the download endpoint.

**CI green validates the configured tests and build; it does not authorize production release or migration.**
