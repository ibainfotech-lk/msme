## 1. Present code and trust boundaries (verified against F.17.5a branch)

| Component | Present behavior | Risk / proposed resolution |
| --- | --- | --- |
| `server/src/config/database.ts` | Requires database `noteto_dev`, port `3307`, user `noteto_services`, then validates connected database and port | Deliberate dev-only safety guard. Do **not** strip it; design a separately reviewed production profile with explicit allowed DB target, identity and network restrictions |
| `server/src/index.ts` | Also hard-checks `noteto_dev:3307` and binds `127.0.0.1`; creates MySQL-backed session store | Keeps the existing server local. Future deployment must intentionally validate networking/proxy and pool settings, not simply set `NODE_ENV=production` |
| `server/src/index.ts` sessions | `noteto.sid`, HTTP-only cookie; `secure` in production; `sameSite=lax`; session stored in DB; `trust proxy=1` in production | Review exact TLS termination and trusted proxy CIDRs/hops; enforce secure cookies, session fixation resistance, inactivity timeout, invalidation, cookie domain/path, CSRF and log redaction |
| `server/src/index.ts` CORS | Credentials allowed for `CLIENT_URL`; development default localhost | Production needs strict single or vetted origin allowlist with HTTPS; **CORS is not authorization or CSRF protection** |
| `checkout-origin.middleware.ts` | Write requests enforce exact `Origin` and validate `Referer` if present; HTTPS origin required in production | Keep these checks; also evaluate CSRF token / server-side anti-CSRF strategy for cookie-authenticated mutations and exact session boundaries |
| `server/src/routes/auth.routes.ts` | Production OTP request/verification return `OTP_DELIVERY_NOT_CONFIGURED`; local dev code logs OTP | Provider/anti-abuse implementation and review required. Never log OTP in any reachable production environment or collect real numbers in synthetic tests |
| `registration-checkout.service.ts` | Development-only; creates pending account and checkout; existing owner baseline is 12 permissions | Separate live registration gate after OTP, identity and consent review; never give new tax permission implicitly or activate unpaid accounts |
| `payment.service.ts` / mock gateway | Commercial Bank adapter not implemented; mock gateway forbidden in production | Keep `MOCK` hard-disabled. Require official merchant contract, signed server verification, idempotency, reconciliation, dispute workflows; no guessed bank endpoints |
| `prisma.config.ts` | Builds migration datasource from `MIGRATION_DB_USER/PASSWORD` and selected DB host/name/port | Use separate migration identity from runtime role; verify environment/tenant and migration target, review SQL before execution, support backup and rollback |
| F.17.1–17.4 routes | Cashbook, invoices, reporting and tax readiness use development guards | Do not alter these until separate authorization. Tax readiness stays permanently outside initial production launch unless separately approved |

**Hard stop:** The existence of a successful GitHub workflow does **not** verify a live deployment, a payment provider, production session security, a tax engine, or the correctness of an unexecuted migration against real data.

## 2. Proposed deployment topology (NOT provisioned)

```text
Customer browser / mobile client
   |
   | HTTPS with monitored TLS
   v
Approved DNS / edge / WAF / rate-limit layer
   |
   | explicitly authenticated and trusted proxy path
   v
Private application ingress / reverse proxy
   |
   | bounded request size, forwarded-header validation
   v
Noteto API (Node.js + Express, container, least privilege)
   |      |       |
   |      |       +-- Approved OTP provider (later, outbound-only with secrets)
   |      +---------- Approved Commercial Bank adapter (later, provider-specific auth)
   +----------------- Private managed MySQL 8.4: runtime role only
                           |
                           +-- Separately authorized migration job / role
Session store: approved private durable store; isolate session permissions.
Backups, key manager, metrics/alerts and audit records managed separately.
```

- TLS must terminate at an approved location; direct public traffic must not bypass edge controls or supply spoofed `X-Forwarded-*` headers.
- Review private-network reachability, port binding and container ingress; `0.0.0.0` is **not** automatically safe merely because the application runs in Docker.
- Database connection must require private routing, encrypted transport as applicable, backup/recovery, least-privilege credentials, encrypted storage and production credentials never shared with CI.
- Use secure, centralized secrets management and rotation; no keys/connection strings in Git, build artifacts, analytics, error payloads or browser bundles.
- Re-check customer data locality and privacy requirements with an appropriately qualified Sri Lankan privacy adviser, including provider/subprocessor assessment.

## 3. Proposed environment identity model (future change; not implemented)

Treat `NODE_ENV` as a runtime optimization flag, **not** authorization to access live databases or customers. Introduce an independently reviewed deployment identity and immutable target binding in a later milestone.

| Identity | Test data | Allowed database | External services | Feature activation |
| --- | --- | --- | --- | --- |
| LOCAL_DEV | Synthetic only | `noteto_dev` explicitly bound; current 3307 guard | No real SMS/bank; mock only | Existing development flags only |
| DISPOSABLE_CI | Synthetic only | Ephemeral MySQL 8.4, test-specific guard token and dedicated credentials | Network provider calls forbidden | Current CI tests only |
| STAGING | Synthetic / authorized masked fixtures only | Dedicated staging DB with independent credentials and target fingerprint | Provider sandbox, if approved | Separate sandbox-only flags, never customer cash capture |
| PRODUCTION | Real customer data only after written go/no-go | Private production DB with unique identity, least-privilege role and approved migration path | Approved live OTP/bank integrations only | Each core feature independently authorized and tested |

**Never** treat a name such as `noteto_prod`, an environment variable, DNS hostname or a self-declared feature flag as sufficient proof of database identity. Bind target identity to independently reviewed deployment metadata, private network/credential boundaries and server-verified database fingerprint. Refuse startup on any mismatch. Do not let CI credentials or token act as production credentials.

Current app logic must remain unchanged until an explicitly reviewed, tested configuration replacement exists. Never reuse local/dev credentials for production or remove the current hard stops ahead of that replacement.

### Future config validator acceptance criteria

- Reject missing/unknown deployment stage, ambiguous `NODE_ENV`, unknown database identity, invalid DB port/host, default development credentials in production, untrusted proxy and non-HTTPS production URL.
- Reject combination of production identity with local/CI database guard, mock gateway, OTP console logging, test payment verification or any F.17.4 tax review flag.
- Reject staging/CI environments with live bank credentials or live SMS routing; maintain separate secret scope and outbound egress rules.
- Validate session secret quality and rotation process, session store lifetime, cookie security and origin/CSRF configuration. Avoid exposing full secret contents in errors.
- Fail closed **before** network connections on invalid configuration; then verify actual connection target and accessible DB privileges before binding HTTP listener.
- Test positive configurations only with fabricated hosts/credentials; no actual production DB/network connections in CI.
- Ensure a request, browser setting, JWT claim or untrusted header cannot select environment identity, bypass tenant/HOLD checks or change gateway mode.

## 4. State and payment safety boundary

- Customer checkout remains **PENDING** until authenticated, provider-verified server settlement or separately verified free-trial/promo activation.
- Keep consistent lock ordering and idempotency: business → checkout → payment / subscription; races and webhook replay must not produce duplicate charges, subscriptions or invoices.
- No frontend redirect, status text, request parameter, uploaded receipt or browser cookie is proof of payment.
- A production gateway adapter must use official current bank documentation, signature/authenticity checks, trusted verification endpoint, amount/currency/merchant/order matching, reconciliation and failure handling. Contract approval is an **open dependency**.
- Production OTP must be delivered via an approved provider, with phone-normalization, per-identity/device/IP rate limits, cooldown, bounded attempts and redacted logs; console output must never disclose OTPs or real phone numbers.
- Trial and promo reservations alone are **not** active subscriptions; eligibility and final activation require a separately approved atomic workflow.

## 5. Request, session and audit boundaries

- Create a reviewed CSRF strategy for cookie-authenticated POST/PUT/PATCH/DELETE, not just CORS. Validate trusted origins and separate bank-signed webhooks from browser session routes.
- Use explicit rate limits for OTP requests, verification, registration, checkout, session creation, profile edits, invoice issuance and API reads susceptible to enumeration.
- Rotate session IDs on authentication; set short-lived OTP-verified registration context; invalidate sessions on logout and sensitive changes. Validate any sensitive endpoint against current DB membership and subscription access each time.
- Separate health endpoints: a minimal unauthenticated liveness check and internal-only detailed readiness (DB/provider dependency) as appropriate; do not leak schema, credentials, tenant IDs or internal topology.
- Enforce structured allowlisted logs with request/correlation IDs; no OTPs, identity document content, account secrets, bank credentials, complete callback payloads or raw customer tax evidence in logs.
- Maintain immutable financial/edit/reconciliation audit records; retention and access policies must be formally reviewed. Never use the tax draft/checklist as authorization to compute tax.

## 6. Migration, rollout and recovery requirements

1. Choose managed MySQL 8.4 hosting, separate production/staging environments, least-privilege application role and **separate migration role**.
2. Review migration history and `main` integration path explicitly; the feature work remains on branches and draft PR #1 is not a production release artifact.
3. Approve migration SQL changes and rollback strategy using disposable and staging exercises; take a tested pre-migration backup/snapshot. Do not run migrations from the web process or ordinary production requests.
4. Rehearse restore to an isolated environment and measure acceptable RPO/RTO with the product owner; define contact escalation and failover responsibilities.
5. Deploy first to staging with synthetic users and gateway sandbox; run auth/tenant/hold, registration, billing, trial, cashbook, invoice, reporting, backup, monitoring and failure-recovery tests.
6. After written security, accounting, legal/privacy and product sign-offs, independently authorize a restricted pilot. Make production rollout reversible, observable and gated by documented go/no-go criteria.

## 7. Planned independent security tests (no code added here)

| Test scenario | Required result |
| --- | --- |
| `NODE_ENV=production` with dev DB/CI marker or localhost fallback | Abort startup before database connection |
| Production config missing managed secrets or TLS/proxy trust | Abort; never downgrade security |
| Spoofed proxy headers or wrong Origin/CSRF on a cookie write | Reject; no state mutation |
| Unauthorized, held or cross-business member | Deny even if frontend enables a feature |
| Development mock success/callback in production | Reject; no subscription activation |
| Live OTP provider unavailable, too many attempts, replay or expired code | Controlled failure, no session/auth bypass |
| Bank webhook missing/forged/replayed or mismatched order/amount/currency | Reject or reconcile without new activation |
| Two concurrent enrollment/payment/activation requests | At most one valid activation or entitlement |
| Migration job with app role or wrong target DB | Reject without schema changes |
| Restore/rollback exercise | Recover safely; document measured evidence and residual risks |
| Tax readiness and professional verification in production | Remain disabled; amounts stay `null` |

Future implementation tests must use disposable CI and provider sandbox contracts; a green workflow alone never constitutes release sign-off.
