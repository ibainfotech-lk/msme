### Documented API binding

- Send endpoint: `POST https://e-sms.lk/api/v3/sms/send`.
- Provider requires `Authorization: Bearer <server-token>`, `Content-Type: application/json`, `Accept: application/json`. **The offline request builder NEVER generates or stores an authorization header**; no secret is required for test execution.
- JSON body: `{ "recipient": "947xxxxxxxx", "sender_id": "NOTETO", "message": "..." }`. The real sender name must be independently approved before external sending.
- API accepts Sri Lankan mobile numbers in `+94...`, `94...`, or local form; the adapter requires one canonical Noteto `+947xxxxxxxx` number and converts only at provider-boundary serialization.
- Successful send API response is `status: "success"` and `data.uid`. This means the gateway accepted a request; **it does not prove delivery or possession of the OTP**.
- Provider error categories are recognized only for deterministic terminal failures; 429/5xx, unknown codes, inconsistent success responses and ambiguous outcomes require reconciliation before any retry.
- The provider documents `GET /sms/{uid}` for delivery/status lookup, but that endpoint is **not implemented yet**. Do not auto-retry a timed-out SMS without an approved deduplication and provider-reconciliation policy.

## Security properties

- No `fetch`, TCP call, request handler, worker, scheduler, database connection, API token, external SDK, message send, OTP generation or session update.
- The adapter is **not imported by `auth.routes.ts` or `otp.service.ts`**. Existing production OTP requests still return `OTP_DELIVERY_NOT_CONFIGURED`, and production registration is still disabled.
- Only one canonical `+947...` number may be serialized; bulk recipient strings and non-Sri Lankan destinations are rejected. Sender IDs must be simple one-to-eleven-character alphanumeric identifiers. The candidate sender `NOTETO` has NOT been approved.
- Adapter output can contain message plaintext because it is a pure payload builder; callers must never write that output to logs, telemetry, exceptions, browser bundles, or persistent test artifacts. Synthetic test codes are not real secrets.
- Provider receipt interpretation returns only an opaque UID or safe reason, never copies untrusted provider error messages (which could reveal credentials, phone numbers or content).
- All output outcomes have `permitsOtpVerification: false`, `userAuthenticated: false`, `businessActivated: false`.
- No amount of test fixture data permits an API call, creates a paid entitlement, verifies a taxpayer or bypasses normal registration/payment security controls.
- No migration: the repo still has **23** migrations; no customer data or production services were touched.

## Integration sequencing — remaining actual work

**External prerequisite:** Obtain vendor written permission for a sandbox/test account, supported sender ID, current official API contract/response semantics, a secure test token, SMS operator coverage, agreed costs, and legally/privacy-reviewed processing. Store tokens **only** in approved secret management, never in chat, repo, CI artifact, or client.

Then implement a separately reviewed and authorized follow-up:
1. Trusted server-side OTP challenge + durable dispatch/outbox record in a disposable/staging DB with bounded expiry and idempotency; approve new migrations and transaction locking separately.
2. Sandbox-only server network transport with pinned HTTPS endpoint, redacted errors, timeout policy, credential scopes, egress allowlist and circuit breaker. No arbitrary URL, redirect or user-specified provider.
3. Provider UID reconciliation via official `GET /sms/{uid}` and receipt state machine. Reconcile uncertain sends **before** retrying; avoid duplicate paid messages and keep provider receipt status distinct from actual OTP verification.
4. Atomic request throttling and anti-enumeration protections, including phone/IP limits, abuse store health, short expiry, five failed verification attempts, resend invalidation, and session rotation.
5. Review actual SMS wording and Unicode segment charges for English, Tamil and Sinhala; write contract/transport-failure and provider sandbox tests using consented synthetic recipients only.
6. Only after security, legal, provider and pilot signoffs: separately implement production-safe OTP routes, registration checkout and real Commercial Bank payments. Do not enable any of them as part of this milestone.
