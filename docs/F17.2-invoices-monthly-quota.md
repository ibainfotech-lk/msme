# Noteto F.17.2 — Cash-basis-safe sales invoices (private development)

**Branch:** `feature/f17-2-invoice-issuance-limits`
**Base:** successful F.17.1 cashbook workflow #34, commit `301375ab7c295f0e893f5294d7b5787d6a58b9ff`.
**Release:** never enable in production until after independent payment, security, legal/tax and financial workflow review.

## Customer rules and implementation

- Issue a sales invoice to a named customer, with optional email/notes and 1–20 item lines (description, quantity, LKR unit price).
- Keep all financial arithmetic in **integer cents / BigInt**, round each line to the nearest cent *half up*, sum rounded lines and reject nonpositive or overflowing invoices.
- Use business-specific, month-specific numbers `NT-YYYYMM-NNNN`. These are ordinary commercial invoice numbers, **not** government-certified VAT/tax invoices.
- A valid ACTIVE or TRIALING business with a current, unexpired period, no hold and the appropriate `invoices.create` permission may issue invoices. Read/list requires `invoices.read`; membership and role must be active and business scoped.
- Only the current **Asia/Colombo calendar month** is eligible for issuance. The server controls the issue date; the browser cannot backdate an invoice. The current subscription plan's invoice limit is respected, with a hard safety ceiling of **30 per month** in this stage. Optional extra-invoice bundles are not implemented.
- **28/30 warning:** `warningAt28=true` beginning with invoice 28. Remaining slots are available in the quota API; **invoice 31 fails with `INVOICE_MONTHLY_LIMIT_REACHED`**. Invoices are immutable ISSUED records in this stage; there is no void, edit, delete, payment or PDF endpoint.
- A transaction first locks the parent business, then the current subscription, permission, existing idempotency reference and monthly count. It inserts an invoice and line items or rolls back everything. Two requests cannot consume the same final slot.
- The same business/idempotency key with the identical normalized payload returns the original invoice. Reuse with a different payload or in a different local calendar month is rejected. The frontend preserves the idempotency key until the server confirms issuance.
- New tables: `sales_invoices`, `sales_invoice_lines`. Both enforce tenant-linked composite foreign keys, invoice number uniqueness, monthly sequence uniqueness, and idempotency uniqueness.
- **A sales invoice does not create an income/expense cash entry.** A customer owing LKR 1,000 is not an LKR 1,000 income receipt. There is no automatic cashbook entry, bank charge, revenue recognition entry, settlement or customer payment allocation.

## Authenticated private-development routes

Mounted under `/api/invoices`:

| Method | Route | Authorization |
|---|---|---|
| GET | `/businesses/:businessId/quota` | `invoices.read`, current full subscription, business-scoped |
| GET | `/businesses/:businessId?limit=50&cursorCreatedAt=ISO&cursorId=UUID` | `invoices.read`, business-scoped keyset |
| GET | `/businesses/:businessId/:invoiceId` | `invoices.read`, same business and invoice |
| POST | `/businesses/:businessId` | session, same-origin write check, `invoices.create`, strict JSON, one MySQL transaction |
| PATCH, DELETE or other methods | — | Disabled (405 under development guard) |

Example POST:

```json
{
  "customerName":"Northern Bakery",
  "customerEmail":"accounts@example.com",
  "notes":"Please pay by the agreed date",
  "lines":[
    {"description":"Delivered goods","quantity":"2.00","unitPriceLkr":"250.00"},
    {"description":"Delivery service","quantity":"0.50","unitPriceLkr":"100.00"}
  ],
  "idempotencyKey":"invoice-request-stable-unique-token"
}
```

The response includes `invoiceNumber`, issue date, `totalLkr`, whether the request was replayed, the monthly quota and explicit `cashbookEntryCreated:false` and `paymentCollected:false`.

## Private UI and production gating

- Backend requires `NODE_ENV=development` **and** `NOTETO_F17_INVOICING_ENABLED=true`. Without both, all invoice API requests return 503, including production.
- Frontend invoice panel requires Vite development mode **and** `VITE_NOTETO_F17_INVOICE_UI_ENABLED=true`. It appears inside the F17 cashbook screen, which separately requires `VITE_NOTETO_F17_BOOKKEEPING_UI_ENABLED=true`.
- The browser's FULL/HOLD mode must be confirmed by the existing server-side access endpoint. Every invoice endpoint independently checks business, subscription and permission again.
- React supports **English, Tamil and Sinhala**. The screen shows 28/30 warnings, authoritative monthly quota, invoice line items and issued history. It prominently states that invoices are not receipts.
- Private development access is not production release permission. The authenticated session is server-authoritative; a UI flag never overrides backend eligibility.

Coverage includes:
- Issue with itemized LKR calculations while confirming **zero cash transactions and zero platform payments**.
- Per-line decimal rounding, immutable idempotent replay, concurrent duplicates and last-slot races.
- Warning at 28, hard cap at 30, lower plan caps and subscription eligibility.
- Tenant isolation and `invoices.create`/`invoices.read` RBAC; trial access; held, suspended and expired denial.
- Keyset history, negative/oversized data rejection, strict HTTP JSON, session and same-origin write enforcement, forbidden DELETE and production disabled before DB connection.

**Do not migrate a customer or local working database using this branch.** A green GitHub Actions run is a development test checkpoint only.
