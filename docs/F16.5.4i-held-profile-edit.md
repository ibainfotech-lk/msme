# F.16.5.4i — Profile editing for subscriptions on hold

**Status:** Private development implementation only; not live and not yet CI validated. This branch derives from the CI-passing verified arrears commit `be0c05f`.

## Customer policy

While an ACTIVE business has a reviewed `PAST_DUE` subscription and a reliable `held_at` timestamp, the owner or permitted `business.manage` member may edit:

- Their own `users.full_name` and `users.preferred_language`;
- A separate **public business display name** (not the legally registered business name);
- Business contact email (not their authentication or registration email);
- Business contact address.

The business's legally registered name (`businesses.name`), registration type, government/tax identity, OTP phone, registration email, identity verification, subscription or membership state, billing periods, bank payments, financial transactions, invoices, prior reports, and report generation **cannot** be modified via this endpoint.

The customer UI displays locked registration data alongside editable fields so the distinction is unambiguous. Empty initial display names are shown as the current registered business name for convenience, without changing the legal record.

## Technical design

An additive migration creates `business_profile_details` (one per business, versioned) and `business_profile_edit_audits` (old/new version and JSON snapshots). The update:

1. Requires authenticated user/session, explicit development feature flag and valid business ID.
2. Locks the ACTIVE business, current `PAST_DUE` subscription, active user, and profile rows. Missing, future or invalid held_at fails closed.
3. Requires active business membership and the existing `business.manage` permission.
4. Accepts only six explicitly allowed values: `expectedVersion`, `fullName`, `preferredLanguage`, `displayName`, `contactEmail`, and `address` (plus business ID from the URL and user ID from the session).
5. Validates lengths, language, contact email, and optimistic version. Never accepts legal identity, phone, email-for-login, tax/billing or subscription columns.
6. Saves personal and contact fields, increments the business profile version and inserts an audit in a **single MySQL transaction**. Any error rolls back.
7. Rejects cross-business edits, missing permission, stale revisions, unchanged updates and admin-suspended businesses.
8. Returns no bank payment or financial operation.

## Development-only endpoints

Both require `NODE_ENV=development` and `NOTETO_HOLD_HISTORY_API_ENABLED=true`; the service additionally requires `NOTETO_HELD_PROFILE_EDIT_ENABLED=true`.

- `GET /api/hold-history/businesses/:businessId/profile`: returns current editable details and locked identifying fields to the authorized user only.
- `PATCH /api/hold-history/businesses/:businessId/profile`: same-origin-checked, strict JSON body; updates only permitted fields, audited.

React's Account Hold screen uses an explicit profile component and has English, Tamil and Sinhala labels. These changes do not add or unlock income/expense creation, invoices, report generation or live payment routes.

## Production safeguards not yet implemented

- Robust CSRF tokens, HTTPS/origin and session end-to-end tests, throttling and security review.
- Least-privilege production database account, audit retention and tamper-evident storage; a privileged database actor can currently overwrite audit rows.
- A profile-edit audit retention/deletion policy for personal data and validated localized copy.
- Business identity-change review for legally registered name/registration details; **never** use contact email as a login or legal verification replacement.
- Automatic hold transitions/restoration, fully reconciled payment gateway and real customer finance flows remain separate milestones.

**Do not apply this development migration to local or production customer databases. First run disposable MySQL 8.4 CI on this branch.**
