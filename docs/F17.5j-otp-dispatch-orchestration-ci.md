## Purpose and implemented scope

F.17.5i added a durable, transaction-guarded OTP dispatch journal in **disposable GitHub Actions MySQL 8.4 only**. F.17.5j now exercises the *ordering* that future authorized delivery must follow:

```text
Existing hashed OTP challenge (CI fixture only)
          |
          v
Reserve journal record with idempotency key
          |
          +--> already reserved/replayed? NEVER send again
          |
          v
Claim exactly one dispatch attempt (DB commit FIRST)
          |
          v
Call injected synthetic port (fake; NO real provider)
          |
          +--> exception, rejection, or ambiguity:
          |       leave DISPATCH_UNKNOWN; no retry
          |
          v
On provider-accepted UID, record acknowledgement
          |
          +--> failed/duplicate persistence:
          |       leave DISPATCH_UNKNOWN; no retry
          |
          v
ACKNOWLEDGED (NOT delivered, NOT OTP-verified)
```

This ensures that a process crash after claim, unknown provider result, callback mismatch, duplicate UID, repeated idempotency key, or concurrent request cannot authorize automatic re-sending.

## Security boundaries and known limitations

1. **Environment hard stop:** The orchestration checks the exact ephemeral GitHub Actions profile before reserving a journal entry or calling the injected port; the underlying journal additionally verifies the **actual disposable MySQL 8.4 identity** and marker. Production, staging, local, unknown or missing flags return `CI_DISABLED` or fail before sending.
2. **At most one claimed send:** Journal reservation is idempotent; a claim commits `DISPATCH_UNKNOWN` **before** the injected send. Any replay returns `REPLAY_NO_SEND`. A different key for the same challenge fails. These invariants are evaluated in disposable MySQL, not inferred from a client cookie.
3. **No automatic retries:** A failed send, unknown status, exception, duplicate provider UID or journal persistence error remains uncertain. The caller never receives a retry permit; a later service must reconcile the exact provider attempt using trusted records and human-reviewed policy.
4. **No authentication:** `otpVerified`, `sessionAuthorized`, `businessActivated` and `resendPermitted` are **always false**. Even a provider-accepted UID proves neither SMS delivery nor OTP possession. Existing OTP verification remains the only code-possession check in private development.
5. **No secrets:** Only fake CI messages, synthetic phone fixtures, test-only HMAC values and in-memory send stubs are used. Do not place real SMS bodies, OTP codes, API tokens, phone numbers, or customer information in GitHub/CI logs or test fixtures.
6. **Not a staging send implementation:** The injected port could theoretically be replaced by a network implementation; **doing so is prohibited** until independently reviewed staging credentials, provider approval, allowlists, egress policy, retention, phone rate limits and operational controls exist. These are not supplied or verified by F.17.5j.
7. **No runtime integration:** Neither `auth.routes.ts`, `otp.service.ts`, registration/checkout, the backend entry point, nor the staging HTTP executor is wired to this orchestration. No API exposes it.
