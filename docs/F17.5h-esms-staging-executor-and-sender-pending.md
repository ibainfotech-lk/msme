## Request restrictions

- Only `POST https://e-sms.lk/api/v3/sms/send` and `GET https://e-sms.lk/api/v3/sms/{uid}` are allowed (from official documentation `https://e-sms.lk/docs`, checked 25 November 2026).
- The caller must supply a trusted backend-only Bearer token, not a user input, browser variable, CI secret or checked-in token.
- Only the `NOTETO` sender ID and explicitly allowlisted **synthetic/consented staging** Sri Lankan mobile numbers are eligible; status lookups require a separately allowlisted message UID.
- Production, disposable CI, a pending/denied sender, absent sandbox approval, missing independent egress review, untrusted credential origin, or empty allowlists cause request denial **before** the injected fetch function.
- Guarded JSON body permits only `recipient`, `sender_id` and `message`; single recipient, no bulk recipients or arbitrary header injection.
- Fixed HTTPS URL, documented method, explicit `redirect:"error"`, strict response URL check, refusal of redirects, five-second deadline and AbortController, maximum 8 KiB streamed JSON response, strict content-type and bounded request body.
- Error messages are generic: upstream exceptions, token, SMS content, phone numbers and provider JSON never appear in the return value or the thrown error.
- A response `uid` means a provider may have accepted the send, **not** that a handset received the message. Any ambiguous send or status becomes `RECONCILIATION_REQUIRED`; no automatic repeat send, OTP possession, session or subscription is granted.

## Critical limitations

This is **not yet a deployed sandbox client**. The fetch-like implementation is deliberately not supplied by the module or imported by any live route, worker, startup file or test runner. CI uses in-memory fake HTTP responses. No production setting or route is changed.

The settings `senderIdApproved`, `providerSandboxApproved`, `egressToProviderApproved` and `credentialsFromSecretManager` are synthetic policy inputs. **They are not independent proofs**. A real staging caller must derive them from secure provisioning controlled by the organization and verify the test-recipient/UID allowlists from trusted server records. No browser or request may assign them.

The client cannot independently enforce cloud egress firewall, DNS resolution restrictions, secret provenance, approved sender activation, per-tenant limits, consent or persisted dispatch identity. Those are mandatory infrastructure/service-level prerequisites, not solved by the fake-fetch tests. The injected fetch implementation must not be wired to a network-capable runtime until those controls are reviewed.
