# Noteto F.17.1 — Core cash-basis bookkeeping (private development stage)

**Implementation branch:** `feature/f17-1-core-cashbook`
**Starting point:** F.16.5.4l passing commit `ae690c7`.
**Status:** Committed for GitHub Actions validation; **NOT production enabled**.

## Scope now implemented

- Manual **INCOME**: money already received by the business.
- Manual **EXPENSE**: money already paid by the business.
- Actual money movement date in `YYYY-MM-DD` using Asia/Colombo local calendar, never a future or invalid date.
- Positive, fixed two-decimal **LKR** amount within `DECIMAL(12,2)` range; category and optional description.
- Affirmative `cashConfirmed:true` field on every create operation. No receivable, payable, expected income, unpaid invoice, or bank payment is created from this cashbook API.
- Secure business-scoped list with keyset pagination by `occurred_on,id` (max 100 at once).
- Correct existing cash entries only when FULL access; requires `transactions.update`, existing business-owned UUID, `expectedVersion`, reason and before/after audit in the same MySQL transaction. Entry type and creator never change. Archived PDF snapshots are not rewritten.
- Multi-tenant checks: authenticated session user, active business membership, role+permission, current ACTIVE or TRIALING subscription, effective start and current period/trial end, not held. A PAST_DUE, suspended, expired, pending, unverified or unauthenticated business cannot add or edit.
- Idempotent create receipt table `cash_transaction_create_requests`: unique (business,idempotencyKey), immutable SHA-256 request fingerprint, same-transaction creation, replay returns same UUID; conflicting payload fails. Business row lock prevents duplicate concurrent creation.
- Dev-only React pilot screen with English/Tamil/Sinhala copy, income/expense form, cash confirmation, paginated history, audit correction form, server error codes and explicit no-report-generation notice.

The legacy numeric-ID routes were removed as active behavior; the old default `503 FEATURE_NOT_READY` remains when flags are off or in production.

## Internal routes (development only)

Every route is mounted under `/api/transactions` and requires a server-side session.

| Method | Path | Additional controls |
|---|---|---|
| GET | `/businesses/:businessId?limit=50&cursorDate=YYYY-MM-DD&cursorId=UUID` | `transactions.read`, active/trial current subscription, tenant filtering |
| POST | `/businesses/:businessId` | Same-origin check; `transactions.create`; cash attestation; idempotency |
| PATCH | `/businesses/:businessId/:transactionId` | Same-origin check; `transactions.update`; optimistic locking + atomic audit |
| DELETE/other | — | Explicitly disabled (405 in private development) |

Create example:

```json
{
  "transactionType": "INCOME",
  "cashConfirmed": true,
  "amountLkr": "1500.00",
  "category": "Sales",
  "description": "Cash received for goods",
  "occurredOn": "2026-11-20",
  "idempotencyKey": "customer-generated-stable-unique-key"
}
```

Correction example (entry UUID in route):

```json
{
  "expectedVersion": 1,
  "amountLkr": "1450.00",
  "category": "Sales corrected",
  "description": "Recounted actual cash",
  "occurredOn": "2026-11-19",
  "reason": "Incorrect cash count in the original entry"
}
```

## Feature gates (NEVER enable in production)

Backend requires `NODE_ENV=development` and `NOTETO_F17_BOOKKEEPING_ENABLED=true`. The React pilot screen requires Vite development mode and `VITE_NOTETO_F17_BOOKKEEPING_UI_ENABLED=true`.

The existing React login invokes server-side subscription access lookup when this UI is enabled. Therefore private pilot testing also needs the reviewed-access route mounted in development with `NOTETO_HOLD_HISTORY_API_ENABLED=true` and its existing policy flag `NOTETO_SUBSCRIPTION_HOLD_POLICY_ENABLED=true`. These flags do not authorize any billing or subscription transition.

**The service performs all permission, business and subscription checks again**; the UI flag never grants access.

## Security and accounting constraints

- No arbitrary changes to business UUID, actor UUID, entry type, tenant, subscription, gateway, invoice or audit data via request body.
- Validation prevents zeros, negatives, malformed decimals, impossible/future dates and empty categories. Type/name mismatches are rejected before SQL.
- SQL is parameterized, and transaction updates use a version check and a tenant predicate.
- A client confirmation is a bookkeeping declaration, **not proof of an externally verified bank transfer**. This stage does not reconcile bank statements.
- Corrections to records represented in earlier reports require care: archived reports remain snapshots and do not silently regenerate.
- A full account may have a valid database status but stale billing; current start/end dates are independently checked in this initial stage. Future reviewed activation/renewal processes remain pending.
- Origin validation is present for writes; stronger CSRF tokens, rate limits, abuse monitoring, least-privilege DB roles, retained audit evidence and production security review remain required.
- User/merchant payment separation is preserved. No payment initiation, invoicing, tax estimate, new report, email reminder, notification worker or account reactivation is added.
