## What is implemented

- `prisma/migrations/20261125_034_otp_dispatch_journal/migration.sql`: two InnoDB tables, `otp_dispatch_records` and `otp_dispatch_events`, with unique request key, unique challenge, optional unique provider UID, one-attempt check, and append-only lifecycle event rows.
- `prisma/schema.prisma`: matching Prisma models and lifecycle enums. The record intentionally has **no FK to `otp_verifications`**, because an OTP is deleted on successful verification; the dispatch record must survive for reconciliation. The service checks the challenge's existence/expiry transactionally before reserving or claiming a send.
- `prisma/migrations/20261125_035_prisma_tenant_one_to_one_uniques/migration.sql`: two explicit, additive composite unique indexes matching existing tenant-scoped 1:1 Prisma relations. Prisma 7.10.1 raised P1012 because the composite defining fields were not marked unique, even though child IDs already had unique indexes. This migration does not alter foreign keys or relax tenant boundaries.
- `server/src/services/otp-dispatch-journal.service.ts`: CI-only, server-gated MySQL operations for reserve, one-time claim, provider acknowledgement metadata, and final delivery metadata. This module **does not communicate with e-SMS** and is not imported by routes or workers.
- `server/tests/otp-dispatch-journal.mysql.integration.test.ts`: tests idempotency, duplicate keys, expired/deleted OTP, concurrent claims, replayed receipts, the absence of authentication/activation, and strict disposable-database guards.
- `.github/workflows/noteto-reconciliation-security.yml`: validates the Prisma schema, runs the existing MySQL migrations and all existing tests against disposable MySQL 8.4, and adds the new journal integration test. Existing migration-count assertions have been updated from 23 to 24.

## Journal transitions

```text
Live, hashed OTP challenge (existing)
            |
            | atomic, keyed reservation
            v
       RESERVED
            |
            | one and only one send attempt claimed
            | before external transport (NOT connected yet)
            v
   DISPATCH_UNKNOWN  -- remains uncertain after timeout/crash;
            |           never automatically re-send
            | independently authenticated receipt (future work)
            v
      ACKNOWLEDGED   -- provider accepted; NOT delivered/verified
            |
            | independently validated status lookup (future work)
            v
     DELIVERED / FAILED
```

Every transition is recorded atomically with a lifecycle journal event. Duplicate event types are rejected by a composite unique key. An existing idempotency key with different request attributes or a second key for one challenge fails closed. A second claim never reissues an attempt.

A consumed, missing or expired OTP challenge cannot be claimed for delivery even if the journal's original expiry timestamp remains in the future.

## Sensitive information policy

- The dispatch tables store only UUIDs, a keyed HMAC-SHA256 recipient fingerprint, a SHA-256 request digest, state, bounded provider UID and timestamps. **No OTP plaintext, phone number, SMS body, authentication token, session ID, tax data or card information** is persisted by this journal.
- The existing `otp_verifications` table still stores the phone and bcrypt-hashed OTP; its lifecycle has not been modified.
- The CI HMAC key is a fabricated test-only environment variable and must not become the real key. An approved future implementation must obtain its own isolated secret and verify key rotation and data-retention policy.
- A provider acknowledgement, delivery status, or even a journal `DELIVERED` event never verifies OTP possession, authorizes login, creates a business or activates a subscription.

## Hard environment gates

The new service rejects requests **before obtaining a database connection** unless the process is an exact disposable GitHub Actions environment with the `NOTETO_CI_DISPOSABLE_DB` marker, explicit `NOTETO_OTP_DISPATCH_CI_ENABLED=true`, synthetic HMAC key and development DB credentials. It also verifies the ephemeral database marker and MySQL 8.4 identity after connecting.

The service is **intentionally unavailable in local development, staging and production** at this stage. This is a disposable-DB implementation checkpoint, not a production or staging rollout. The application authentication and registration routes, private e-SMS executor and provider settings are unchanged.
