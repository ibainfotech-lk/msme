# Noteto F.16.5.4e — Historical Income/Expense Correction Audit

**Development-only foundation, not a live transaction service.** Implemented on isolated branch; must pass CI before merge or deployment.

## Hold-mode contract

Customers whose current subscription is **reviewed PAST_DUE** may correct an income or expense entry that already existed **before** the verified `held_at` timestamp. They may not create new income, expense, invoice or report records. They may view/download separately archived, previously generated reports if authorized.

The internal function `editHistoricalCashEntry`:
1. Fails closed unless `NODE_ENV=development` and `NOTETO_HISTORICAL_EDIT_ENABLED=true`.
2. Requires existing UUID-based `cash_transactions`, active business, current subscription `PAST_DUE` and trustworthy `held_at`.
3. Verifies the user's active business membership and `transactions.update` permission.
4. Verifies the target transaction is from the same business and that its **original creation timestamp predates the hold**. It cannot upsert or insert an accounting transaction.
5. Allows correcting amount, category, description and transaction date, but **never changes the income/expense type**. An updated transaction date cannot be later than the Sri Lankan local hold date.
6. Requires `expectedVersion` and uses a business -> subscription -> transaction locking order; concurrent or stale updates fail closed.
7. Updates the entry and writes a detailed **before/after audit record** in the same MySQL transaction; any error rolls back the entire change.
8. Never generates a report. Previously archived PDF snapshots remain unchanged.

The migration defines `cash_transactions` and `cash_transaction_edit_audits` with strict business/entry foreign keys, a unique edit revision, monetary constraints and an index for business-owned history.

## Important work still required

- The existing `/api/transactions` routes remain disabled (503). This stage **does not permit live income or expense creation**, even for otherwise paid customers. A safe, audited create/read/edit API and the correct business-level authorization must be built and independently tested.
- There is no reporting generator, report list/download API, or customer-facing hold UI wired up yet.
- A trusted subscription hold transition, grace-period policy, reactivation and billing notifications are not implemented here.
- Database administrators can alter the audit table using privileged access. Production needs a least-privilege runtime account, tamper-evident audit retention/backups, monitoring, retention and lawful deletion controls; do not claim fully immutable audit protection yet.
- Before real users, require data migration/backfill for historical records, accounting consistency checks, rules for closed tax periods, and per-entry historical report caveats.
- All MySQL tests are **destructive CI-only fixtures** on the disposable GitHub Actions MySQL 8.4 database. Do not run them locally or deploy migration 025 to production.

**Success in CI validates the guarded code and schema only; it does not mean that customers can use hold-mode edits yet.**
