## API facts checked

Official documentation: `https://e-sms.lk/docs`, reviewed 25 November 2026.

- Send: `POST https://e-sms.lk/api/v3/sms/send`, HTTPS JSON with server-only Bearer token; body has `recipient`, `sender_id` and `message`. An accepted `uid` is **not** proof of delivery.
- Status: `GET https://e-sms.lk/api/v3/sms/{uid}`; a delivery report is **not** proof of OTP possession.
- On a send timeout, never blindly repeat the SMS. Reconcile the previous request through provider logs/list/status before authorizing any new attempt; provider status checks are only useful once a UID exists.
- Normalized Noteto phone number is `+947xxxxxxxx`; provider serialization uses `947xxxxxxxx`. English, Tamil and Sinhala templates must be checked for segment billing and approved sender text.
- The tests use only in-memory synthetic responses. **No vendor request was sent.**

## Explicit trust boundary

The module **does not import `fetch` or `https` and contains no built-in network client**. A caller must deliberately inject `EsmsHttpExecutor`; GitHub tests inject a fake executor. No existing auth route, registration service, worker, payment service or startup file imports the new adapter.

The transport is *restricted to an explicit STAGING profile* and requires positive sandbox/sender/credential flags. Those flags are **not independent security proof**. Before any real executor is connected, a future trusted server component must derive them from validated provisioning and provider contracts, not browser input, HTTP request bodies, or mutable user-facing settings. `PRODUCTION` and `DISPOSABLE_CI` always return `SANDBOX_DISABLED` without executing the client.

The injected executor is responsible for enforcing HTTPS certificate trust, fixed-origin allowlisting, rejecting redirects, an actual 5-second timeout, an 8 KiB response body maximum, verified response decoding, safe bounded resource usage and redacted errors. The module requests these controls but **does not itself enforce them**. Therefore it is not independently safe to combine this interface with an arbitrary HTTP implementation.

A staging sender must additionally check an **independently approved synthetic/consented recipient allowlist** and **server-stored dispatch binding** before sending or looking up a UID. The input flags in this test-only adapter are not sufficient authorization. Require signed-off real security middleware and persistent state before live sandbox integration.

The output never includes the token, recipient or original message, and no exception text is propagated. Unknown send results require reconciliation and never trigger automated retries. The adapter cannot verify OTPs, authenticate users or activate subscriptions.
