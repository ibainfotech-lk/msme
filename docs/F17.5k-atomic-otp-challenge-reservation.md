## Why this step matters

The existing private-development `createOtpChallenge()` creates only a hashed OTP challenge and returns the plaintext OTP to its trusted server-side caller. F.17.5i added a separate idempotent dispatch journal; F.17.5j exercised claiming a preexisting challenge and calling an in-memory synthetic port. Before any real SMS delivery can be authorized, generation and reservation need a reliable all-or-nothing transaction.

**This F.17.5k implementation proves the atomic database boundary in disposable CI only. It does NOT send a generated code, and it is not yet a staging or production OTP flow.**

## Invariants enforced

1. **Atomic commit:** a newly generated hashed challenge, its RESERVED dispatch and corresponding journal event commit together. An error inserting an event rolls back both the OTP challenge and dispatch record.
2. **No OTP plaintext escape:** the random six-digit code is generated and hashed inside the CI service, never returned to the caller, sent to e-SMS or saved as plaintext. The resulting snapshot provides only opaque IDs and safe state fields. No system can actually receive/verify the discarded code from this new function; this is deliberate until a trusted delivery execution boundary is designed.
3. **Idempotency:** an exact key + canonical phone can replay the same **still-active** challenge and original dispatch, but cannot create a new code or trigger sending.
4. **Single active challenge:** a second key for the same active phone is rejected. An expired challenge may be replaced with a *new* key; the historical dispatch audit remains untouched.
5. **Consumed challenge cannot resurrect:** if a verified challenge was deleted, retrying the old key fails instead of generating another code.
6. **Concurrent requests:** MySQL unique phone/key constraints and a transaction prevent multiple active OTP challenges for one recipient.
7. **Disposable-only guard:** production, staging, local development and unmarked databases cannot call this function. An actual CI MySQL 8.4 identity and ephemeral marker are verified before entering any transaction.
8. **No user/session/payment authorization:** the function never verifies an OTP, authenticates a session, activates a business, creates a subscription, or grants a resend.

## Integration test cases

- A generated bcrypt hash exists, is not plaintext, and the journal links exactly to its challenge.
- A repeated idempotency key returns identical opaque identifiers and a replay status.
- Reuse of a key for another recipient is rejected.
- A second key is rejected for an active phone.
- Expired challenge replacement requires a fresh key and retains prior audit records.
- Deleted/consumed challenges cannot be recreated using the old key.
- Concurrent competing reservations for the same phone yield no more than one active challenge.
- Simulated event-insertion failure verifies rollback of challenge and dispatch.
- Production and missing-CI switches reject before database connections.

## Known constraints / remaining steps

- **No SMS can be delivered from F.17.5k.** The OTP code generated here is not handed to a sender. An eventual separately reviewed implementation must securely retain the plaintext code **only in process memory during an authorized send attempt**, never in a database/log, and atomically associate it with the correct hashed challenge and dispatch record. The future outbox design needs an explicit recoverability decision: a crash after reservation but before sending must not silently send a different code or double-charge for SMS.
- The current development `createOtpChallenge()` has not been modified; these are distinct codepaths. A later security review must decide how to consolidate them safely.
- The synthetic CI setting is not production attestation. Do not copy CI marker, dummy DB password, fake HMAC key or synthetic approval flags into staging/production.
- Do not modify customer registration routes, e-SMS provider settings or the user-facing OTP workflow until the approved `NOTETO` sender ID, authorized recipient list, provider contract, rate limits, privacy policies, staging secrets and security reviews exist.
- **Commercial Bank verified payments, subscription activation, and production bookkeeping/reporting are separate launch blockers.** Tax payable remains disabled.
