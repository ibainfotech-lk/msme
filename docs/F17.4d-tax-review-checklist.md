# Noteto F.17.4d — Taxpayer Review Checklist (Private Development)

**Branch:** `feature/f17-4d-tax-verification-checklist`
**Base:** F17.4c green GitHub Actions workflow #47, commit `7bda5fd023890d993c5ceacc24b29ea8cd6808a7`.
**Scope:** Read-only derived checklist; no new database migrations, rates, tax calculations, permissions, payments or taxpayer identity storage.

## What the new feature does

A business's existing unverified F17.4c taxpayer intake draft is projected into a seven-item checklist for tax-professional review.

1. Who may be the taxpayer (individual/company/other/unknown)?
2. Claimed tax residency.
3. Is the business owner personally liable?
4. Is there income outside Noteto cashbook?
5. Are capital assets, including furniture and machinery, present?
6. Are any costs potentially nondeductible for tax?
7. Are there withholding taxes or credits to investigate?

The system counts **answers provided**, not **facts verified**. `UNKNOWN` and `NOT_SURE` count as missing; `YES`, `NO` or a declared category count as answered, but all remain `SELF_DECLARED_UNVERIFIED`.

**Crucial:** Even seven fully answered items do not verify residency, taxpayer identity, tax category, other income, deductible expenses, personal relief, capital allowances or withholding claims. A full checklist is not approval. `taxableIncomeLkr`, `taxPayableLkr`, and `paymentDueLkr` always remain `null`, not zero.

## Security / API

`GET /api/taxes/businesses/:businessId/review-checklist?assessmentYearStart=2026`

- Requires `NODE_ENV=development` and `NOTETO_F17_TAX_READINESS_ENABLED=true`, an authenticated session, exact tenant membership, `taxes.read` permission, and a valid active/trial business subscription.
- **Held/suspended/expired accounts cannot access this endpoint**, because the handler calls the existing `readTaxIntakeDraft` service with its complete business, subscription and HOLD checks.
- Strict query validation: extra query parameters are rejected.
- Only the expected enum-based answers are processed; no documents, personal IDs or monetary amounts are added.
- No new write/approve/revoke endpoint is introduced. The original F17.4c `taxes.manage` requirement for writing drafts is unchanged and never granted automatically.
- No new tables or migration: the total stays **23**.
- Results return `Cache-Control: private, no-store`.

The multilingual React component is inside the F17.4c private tax questionnaire gate, with English/Tamil/Sinhala field labels. It re-fetches after successful draft writes, so it does not mistake locally edited unsaved answers for recorded evidence.

## Testing

- New pure policy test suite covers empty, incomplete, full and historical assessment-year drafts.
- Existing disposable MySQL HTTP integration suite extends coverage to unauthenticated, cross-tenant, malformed, and non-GET requests and verifies the change from 0/7 to 2/7 recorded answers after saving a draft.
- The existing GitHub Actions reconciliation-security job runs the new pure policy tests; the disposable MySQL 8.4 job continues to run `npm run test:mysql-tax-readiness`.

**CI is not verified until a fresh run passes.**

## Future professional verification work

Before enabling a tax estimate, separately design a reviewed verification process with:
- Explicit data consent and legal retention policies for any sensitive personal/tax evidence.
- Appropriately authorized accountant/tax reviewer roles with revocable permissions, not inherited global role assignments.
- Immutable reviewer decisions, evidence references, legal version validity, assessment-year linkage and change-triggered re-review.
- Approval workflows preventing self-approval, bypass and claims-based privilege escalation.
- A deterministic effective-dated tax engine only after reviewed statutory rules, taxpayer classification, cashbook-to-tax-base adjustments and IRD test cases are approved.

This stage **does not** file returns, calculate due amounts, create invoices, change cash entries, grant a relief, alter account holds, or touch production data.
