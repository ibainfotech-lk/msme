# Noteto F.16.5.4k — Reviewed hold candidate journal

**Private development foundation, not a subscription hold executor.**
Branch built from the CI-passing `feature/f16.5-4j-hold-lifecycle-review` commit `3585beb`.

## Goal

Keep an idempotent journal of policy-ready hold/restoration *review candidates*, while ensuring that no candidate itself changes a customer's subscription or starts a payment.

The new additive migration `20261123_027_hold_transition_review_journal` creates `subscription_hold_review_journal` with strict business/subscription foreign key, reviewer foreign key, unique idempotency key per business, transition type, an evidence SHA-256 digest, statement as-of, recorded outstanding amount, notice reference, grace deadline, reason and timestamp.

The `recordHoldReviewCandidate` internal function validates the F.16.5.4j pure review policy, then uses a single MySQL transaction to:
- lock and verify the ACTIVE business and current same-tenant subscription, with a matching recorded hold timestamp;
- check the reviewer user has an ACTIVE business membership and `billing.manage` permission;
- reject missing/wrong current subscription, wrong status, stale claim, or unauthorized reviewer;
- insert one `POLICY_READY` journal candidate, or replay an exact same candidate with the same business/idempotency key;
- reject an idempotency-key reuse with different transition, evidence, reviewer or reason.

All writes target the journal table. The service does **not** update `business_subscriptions.status`, `held_at`, `subscription_events`, `businesses.status`, monthly dues, allocations, invoices, income/expense, archived reports, or bank payments.

## Critical trust limitation

**A POLICY_READY journal row is NOT a verified authorization for an actual customer hold or restoration.** This stage accepts a policy evidence object supplied by an internal caller. It does not independently load actual billing, notice-delivery, fraud/dispute, pending gateway attempt, trial, or promotion proof in a single consistent database snapshot. A later implementation MUST verify all evidence from trusted server-side repositories, within the same locking/settlement boundary, before a real state transition.

The reviewer check here is business `billing.manage` membership, **not a full independent internal platform-operator approval system**. That distinction must be resolved before production. A customer-supplied body or browser request must never invoke this service.

The service has **no HTTP route**. It is additionally hard-gated to the disposable GitHub Actions CI MySQL 8.4 environment with an explicit `NOTETO_HOLD_REVIEW_JOURNAL_ENABLED=true` test switch. It cannot execute in the production runtime.

## Tests and CI

The new `hold-review-journal.mysql.integration.test.ts` suite checks:
- a candidate hold leaves the subscription ACTIVE and has no payments;
- a restoration candidate leaves a subscription PAST_DUE;
- exact replay returns the same review ID, while different evidence with the same key is rejected;
- missing manual review, unpaid restoration, cross-tenant subscription, missing reviewer permission and concurrent duplicate submissions fail closed;
- production and feature-disabled paths reject before DB access.

Prisma migration count becomes **18**, and existing disposable integration tests are updated accordingly. GitHub Actions now runs the new MySQL suite. The migration is **for disposable CI only**: do not run against real customers.

## Next release gates

Before an actual state-changing transition service, build approved notice/grace records, complete verified payment and monthly-due history, full promotion/trial eligibility verification, dispute handling, independent reviewer authority, audit retention with tamper-evident controls, concurrency/transactional outbox, customer notifications, restore-after-settlement behavior and end-to-end tests. The current production registration and transaction routes remain disabled.
