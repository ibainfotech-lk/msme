## Existing code and deliberate boundaries

- `server/src/services/otp.service.ts` generates a six-digit OTP with a cryptographically secure random source; stores a bcrypt hash in MySQL; applies five-minute expiry, up to five verification attempts, and deletes the challenge on success. This is development-only through the current HTTP layer.
- `server/src/routes/auth.routes.ts` rejects both OTP request and verification under `NODE_ENV=production` with `OTP_DELIVERY_NOT_CONFIGURED`. In isolated local development the code is printed to the server terminal; this **must not** be exposed on a shared/production server.
- `server/src/modules/checkout/registration-checkout.controller.ts` requires recent session-backed verified OTP for registration and is explicitly disabled outside development. This boundary remains intact.
- F.17.5c's proposed environment preflight is also not connected to startup and cannot authorize SMS, deployments, DB connections or customer records.

The policy has **no imports from the application**, no SMS SDK, no secrets, no OTP plaintext, and no database/network calls. It is intentionally **not invoked by any API or production service**.

## Candidate delivery contract (not a real endpoint)

A future server-side caller would derive, from trusted state, an opaque request UUID, challenge UUID, E.164 recipient, purpose (LOGIN/REGISTRATION), language (en/ta/si), five-minute lifetime, attempt count, distribution-aware phone and source request quotas, cooldown, abuse-store health, suppression check, Origin/CSRF decision, and verified synthetic-recipient status. The policy proposes per-phone maximum 3 requests/window, per-source maximum 10/window, and 30-second cooldown **as provisional limits**, not fully designed production controls. The future security team must define real window lengths, phone/IP/device abuse protections, privacy, throttling and escalation.

The policy recognizes:
- `LOCAL_DEV`/`DISPOSABLE_CI` using a synthetic `STUB` transport only.
- `STAGING` using `SANDBOX` transport only when independently approved and credential scope is validated (the boolean snapshot in a test **does not** constitute real approval).
- `PRODUCTION`: **always denied**, even if a caller claims live provider credentials, until a separately reviewed adapter and rollout exists.

Any plausible synthetic dispatch candidate returns `CONDITIONS_MET_NOT_AUTHORIZED`, which is a **non-authorizing preflight**, not approval to send SMS.

## Proposed provider receipt contract

An actual provider integration must use official documented response and callback formats. The future service would validate an opaque provider message ID, bind the provider response to the original request/challenge and tenant/session, verify authenticity using provider-specific cryptography/transport, and reject mismatched, replayed or untrusted responses. A `QUEUED` or `ACCEPTED` status is only transport metadata; a `REJECTED` or unknown result is not eligible to advance the workflow.

**Never treat a provider acknowledgement, redirect, browser response, callback or receipt as proof of OTP possession.** Only the separately reviewed, one-time, server-side challenge verification process may establish an OTP-verified session. That session still does not grant subscription activation or payment settlement.

The proposed preflight **does not actually validate cryptographic signatures** or determine whether the provider delivered a message. Future API code must verify authenticity; request-supplied `providerResponseAuthenticated` is never proof.

## Immutable no-action fields

Dispatch policy outputs always:
- `sendsMessage: false`
- `authorizesDelivery: false`
- `createsOtpChallenge: false`
- `verifiesOtp: false`
- `authenticatesUser: false`
- `activatesBusiness: false`

Provider-receipt policy outputs always:
- `providerMessageRecorded: false`
- `userVerified: false`
- `sessionAuthorized: false`
- `activatesBusiness: false`

These are **deliberately not operational delivery or receipt handlers**.

## Testing requirements and future work

F.17.5d synthetic tests reject missing facts, production requests, non-E.164 recipients, unsupported purpose/language, absent trusted origin/CSRF/abuse/suppression state, quota or cooldown violations, expired/future/overlong challenges, exhausted attempts, unsafe provider modes, unapproved staging credentials, forged/mismatched/duplicate provider acknowledgements, and provider rejections.

Before connecting a real provider, require independently reviewed:
1. SMS provider onboarding/contract, approved Sri Lankan delivery coverage, sender ID, sandbox account, current API schema, delivery guarantees and pricing.
2. Legal/privacy assessment of phone numbers, message text and delivery/retention records; translations in Tamil, Sinhala and English.
3. Actual distributed quotas and attempt limits with atomic counters, cooldown, secure and abuse-resistant identity normalization, enumeration resistance and rate-limit fail-closed behavior.
4. Explicit HTTP Origin/CSRF/session controls, request-scoped idempotency and challenge lifecycle transactions. Plan around failures where a provider submits a message but DB persistence or session-save fails.
5. Provider-specific authenticated callbacks and server-side verification; secrets rotation, request signing, webhook replay rejection, sandbox adversarial tests and redacted telemetry.
6. Provider outage, SMS delay, out-of-order delivery, lost phone, resend, duplicate/new challenge invalidation, SIM-swap considerations and support incident playbooks.
7. End-to-end synthetic staging tests, human security/financial review, production-release go/no-go and separate runtime configuration replacement.

Do **not** log real OTPs or phone numbers, send real SMS from GitHub Actions, create a live provider adapter from guessed endpoints, or remove current production HTTP guards.
