## 1. Why this milestone exists

The existing `server/src/config/database.ts` and `server/src/index.ts` intentionally hard-lock Noteto to local `noteto_dev`, port 3307, user `noteto_services`. Production OTP and Package 1.0 feature routes are likewise blocked. Removing those checks before a reviewed replacement would create serious operational and customer-data risk.

F.17.5c therefore creates a **separate, unconnected** candidate configuration policy. It can identify common unsafe proposals without weakening the existing server guards.

## 3. Four deployment profiles

| Profile | Proposed acceptable test facts (not authorization) | Must deny |
| --- | --- | --- |
| `LOCAL_DEV` | `NODE_ENV=development`, local `noteto_dev:3307`, local origin, no real provider | Production credentials, live bank/SMS, production data or features |
| `DISPOSABLE_CI` | `NODE_ENV=development`, disposable MySQL 8.4 guard, synthetic fixtures, no real outbound provider | Missing CI marker, live providers, non-dev database |
| `STAGING` | Separate staging database identity, HTTPS, private network/TLS/roles, session/edge protections, disabled or sandbox providers | Production/live credentials, unrestricted feature flags, customer data |
| `PRODUCTION` | A **placeholder design condition** using a distinct private DB, verified network/TLS/roles, HTTPS, sessions and edge checks; **provider modes must remain DISABLED in this policy** | Mock or live gateway, console or live OTP, customer data, tax, bookkeeping/invoice/report production flags |

**This production preflight is intentionally incapable of representing a live customer-facing launch.** Even an all-true *candidate* cannot authorize startup, customer data or provider requests. A future production readiness implementation will need separately signed-off live provider support and a different permission model.

## 4. Always-denied authority fields

Every policy result, including a synthetic `CONDITIONS_MET_NOT_AUTHORIZED` result, guarantees:

- `authorizesStartup: false`
- `authorizesDeployment: false`
- `authorizesDatabaseConnection: false`
- `authorizesProviderCalls: false`
- `authorizesCustomerData: false`
- `enablesProductionFeatures: false`

No client-supplied stage, header, feature flag, test result or environment variable can convert this policy into live deployment authorization. **Never connect this function to application startup as an approval gate without a separately reviewed design and trusted attestation implementation.**

## 5. Synthetic negative test coverage

- Missing or unknown deployment stage; mismatched `NODE_ENV`.
- Local/dev database or CI marker masquerading as production.
- Untrusted host, wrong database identity, root runtime role, missing private network/TLS, shared migration identity or unverified target.
- Non-HTTPS production origin, localhost in production, embedded URL credentials, path/query/fragment injection and malformed URLs.
- Weak secure/HttpOnly cookie, no private session store or missing proxy/TLS/CSRF/rate-limit controls.
- Mock/sandbox/live payment in the provisional production profile; console/sandbox/live OTP; mock settlement flags; live provider in CI or staging.
- Any production user-data, tax, bookkeeping, invoice or report enablement.
- Even the synthetic success fixture never grants any operational capability.

All tests use fabricated domain names and facts, no external calls, no generated secrets, no actual payments and no customer data.
